# 测试场景 FP-015：时间线聚合与排序

对应验收标准（任务卡 §7）与独立验证方式（§8）。测试文件：`tests/test_timeline.py`，运行 `python3 -m pytest -q`。

种子约定（§6）：用户 A(id=1，查询主体)、B(id=2)、C(id=3)、D(id=4，未关注)；关注边 A→B、A→C；帖子 B×2（t1、t4）+ C×2（t2、t3，与 B 交错）+ A×1 + D×1，`t1<t2<t3<t4`（显式时间戳直插 SQLite），倒序结果唯一可断言（t4→t3→t2→t1）。空态场景使用无关注边变体种子（A 自己有帖）。另以内存契约替身（users / posts / follows 集合模拟）重放核心断言，验证服务仅依赖 §3.2 契约形状。

## TC-01 范围正确性（验收 1 / §8 范围）

- **前置**：完整种子（A 关注 B、C；B/C 各 2 帖；A、D 各 1 帖混入全站）。
- **步骤**：`getTimeline(A)`。
- **期望**：返回恰 4 条，作者集合 = {B, C}；不含 A 自己的帖子、不含未关注者 D 的帖子；B / C 的全部帖子无遗漏（按帖子 id 集合断言完备）。

## TC-02 倒序正确性（验收 1 / §8 倒序）

- **前置**：完整种子（B 与 C 的时间交错设计）。
- **步骤**：`getTimeline(A)`，取返回条目的 `created_at` 序列。
- **期望**：严格降序 t4→t3→t2→t1，与种子唯一倒序一致（t4=B、t3=C、t2=C、t1=B 的作者交错模式一并断言）。

## TC-03 空态返回空集合（验收 2）

- **前置**：变体种子——A 无任何关注边，A 自己有 1 帖、B/C/D 有帖。
- **步骤**：`getTimeline(A)`。
- **期望**：返回 `[]`（空集合，且不含 A 自己的帖子）；查询主体不存在的 id 同样返回 `[]`。

## TC-04 排序按时间瞬间而非字典序（边界）

- **前置**：种子中最新一帖 `created_at` 带 `+02:00` 偏移（字典序排会在错误位置）。
- **期望**：仍按真实瞬间排在最前；naive（无时区）时间戳视为 UTC 参与同一序。

## TC-05 同时刻并列（边界）

- **前置**：B 与 C 各有 1 帖 `created_at` 完全相同。
- **期望**：不抛错；两条均在结果中（集合断言），相对次序不限定（契约允许）。

## TC-06 作者信息补全口径（§4，取「本任务补齐」）

- **前置**：完整种子。
- **期望**：每条目携带 `author_id` 与 `author_username`，且与 `getUserById` 查得的用户名一致；字段与帖子四字段（id / content / created_at）并存；返回条目为副本——修改返回对象不影响后续查询结果。

## TC-07 存储顺序无关性（§3.2「顺序不保证」）

- **前置**：内存替身以乱序（倒序预排）返回 `getPostsByAuthorIds` 结果。
- **期望**：`getTimeline` 输出仍为 `created_at` 倒序（排序责任在本任务，不依赖存储顺序）。

## TC-08 关注变化即时反映（联调面，FP-011 数据来源）

- **前置**：完整种子。
- **步骤**：`addFollow(A, D)` 后再查 `getTimeline(A)`；随后移除该边对应数据（重建变体）验证仅关注者集合决定范围。
- **期望**：新关注立即纳入该作者帖子（5 条、含 D 的帖子且倒序保持）；关注集合是唯一范围来源，自己的帖子任何情况下不出现。

## TC-09 内存契约替身路径（§6 Mock）

- 用内存替身（users 字典 + posts 列表 + follows 集合）替代 `DataStore` 重放 TC-01/02/03 核心断言：范围、倒序、空态、作者补全与真实存储一致；替身中作者缺失的帖子 `author_username` 为 `None`（防御口径，不崩溃）。
